# Cabal test extensions

Run `forge build` and `forge test`. No additional dependencies, RPC, environment variables, FFI, or configuration changes are required. The original contributor tests retain their behavior; their gate deployment helper uses the flat constructor and body assertions reflect the audited validity fix.

- `GateLaunch.t.sol`: gate-only factory deployment with the nineteen manifest words. `GateEmptyEvmLaunchTest` deploys in an EVM where the hook, PoolManager, Intake, IMD and CABAL addresses have no code, as the launch checks do. `GateLaunchTest` uses a mock hook at the live address that reports initialized, poolKey, poolManager, imd, cabal and gate like the live one: both internally created helpers, owner control, constructor validation (including the pool words), size/opcode bounds, one-time hook handoff refusing a second gate, a gate with swapped token roles refused by the hook, a buy and a sell request that succeed only once the hook reports this gate, requests refused (without payment) when the hook reports another key, CABAL, IMD or gate, and the owner's live reconfiguration checks plus the oracle's 2..300 panel bound.
- `GateFactoryEdges.t.sol`: bounded constructor fuzzing and pinned numeric edges; rejection of truncated ABI data and dirty upper bits in addresses/narrow integers; separate helpers created by each gate without changing the existing hook/token dependencies; helper rollback after failed constructor validation; mismatched hook/CABAL getters and repeated binding; two-step owner handover; the supplied protocol digest/signature vector and exact fifteen-field callback selector. The generic Sepolia/array vector exercises the production digest library; gate callbacks remain mainnet/bool-only.
- `GateLiveHook.t.sol`: the gate against the real `CabalHook` runtime placed at the live hook address `0xf41b…a0c0` in the test EVM (no deployment transaction), in the state launch 953 left it: the one `beforeInitialize` call is replayed from the PoolManager's address with the manifest key, so the hook reports initialized, CABAL, IMD, the key and an unset gate exactly as read on 2026-10-08, and is owned by `0xfc3c…1774`. Pins that the live address carries exactly the hook's permission bits, that the real `poolKey()` return data is the five-word encoding the gate hashes, and that the real `setGate` refuses non-owners, codeless or getter-less candidates, a gate with swapped token roles and any second gate while accepting the deployed one once. Buy and sell requests are refused before binding and succeed after it on the live addresses, followed by an approval, a rejection, a consumed-attestation replay against the same and another request, and a clear. Requests are refused without payment when the hook has no code, when `poolKey()` reverts, when the same key is returned in a different encoding (trailing word, truncated, dynamic offset, empty), and off mainnet before any hook read. `GateHookReadFuzzTest` fuzzes every pool-key field and the CABAL/IMD/gate reads on the storage-backed mock (512 runs each): a request goes through only when every read equals what the gate was built from, each refusal costs nothing, and the same request succeeds once the reads match again, with pinned one-bit near misses. `GateEmptyEvmUsageTest` shows the gate deployed in the launch rehearsal's empty EVM is inert but intact: submissions and reconfiguration revert and ownership handover still works.
- `invariant/GateOnlyRequests.t.sol`: two gate-only invariants checked over 256 sequences × 64 actions, using the initialized-hook mock and the gate's own helpers. Three actors mix buys/sells at submission, variable oracle prices (including zero), approval/rejection under the 200,000-gas stipend, timeouts, configuration changes, donations, unauthorized calls, bad signatures, and failed payment attempts. Independent per-user ghosts assert exact spending and retained donations; historical configurations, replay records, binding and request lifecycle must remain consistent. A deterministic test confirms the success/failure branches are reachable. These campaigns exercise request custody; the existing real-PoolManager campaigns cover trade settlement.
- `OracleLatency.t.sol`: request-body-derived expiry at delivery delays of 899, 900 and 3599 seconds, with the full five-minute approval available and successful execution at its last second.
- `OracleSigner.t.sol`: reproduces and pins the existing ECDSA-only signer limitation with a valid ERC-1271 registry response.
- `AdversarialOracle.t.sol`: post-signature mutation of every one of the fifteen attestation fields plus the answer encoding; domain name/version/chain/verifier binding; high-s, invalid-v and malformed-length signatures; callbacks with unavailable external dependencies; zero-price and zero-ID handling; failed payment retry; terminal-request replay; attestations issued before submission; identical questions from different users or after a rejection; the zero and explicit `oracleVerifier` settings; timeout boundaries; every invalid owner configuration boundary and the largest accepted values.
- `QuestionProperties.t.sol`: independent JSON-parser round trips over untrusted printable ASCII, quotes, backslashes, DEL, injection-shaped text, empty reasons, all UTF-8 widths at 280/281 characters, and malformed UTF-8; every control character and the guillemet delimiters refused in any position while other characters sharing their lead byte pass. Checks that the stored escaped question is what a parser reads back, that the callback's `questionHash` is the canonical sorted-key keccak of the parsed body with the attested window, the immutable JSON policy fields, the per-definition limit, and the 2000-character bound at the widest values the gate can print.
- `EconomicProperties.t.sol`: fee and price arithmetic boundaries, real swaps across the 400-unit fee threshold, repeated buy/sell cycles without profit, allowance failure/retry, sell-slippage rollback including cost basis and pool price, a seller whose balance dropped between approval and execution (refused atomically, executes once restored), and a sell larger than the tracked holdings (record zeroed, no underflow). Each fuzz property runs 1,000 cases.
- `ReasonEscaping.t.sol`: the revision's single-pass validate/count/escape routine (`Json.prepareReason`) held to an independent UTF-8 decoder that classifies by decoded code point, to the library's own reference `length`/`escape` functions, and to Foundry's JSON parser. Well-formed text of every width with quotes and backslashes (1,000 cases), arbitrary bytes (1,000), and well-formed text with one corrupted byte (1,000) must be accepted or refused with the same error class and escape identically. Pins the byte bound before content and the scalar bound after it, escaping between multibyte characters, and a lead byte at the end of a word-aligned buffer followed in memory by valid continuation bytes, which only the bounds check can refuse (verified to fail against a copy of the library with that check removed).
- `HookBinding.t.sol` (both currency orderings): the revision's sender-agnostic pool binding. Pins the trust assumption that deployment and initialization are atomic by showing a third party who initializes first binds the hook to their own token for good; native currency, misordered and same-currency keys and keys naming another hook are refused; an independent LP router seeds, donates, claims fees and unwinds before and after the gate is bound while its swaps are always refused; the fee state machine armed by `afterSwap` blocks swaps and compounding until the gate settles, a sub-threshold volume clears unpaid, exact-output and non-gate senders are refused in `afterSwap`; permissionless `compound` with unowned, inverted, misaligned or full-range ticks reverts without a trace.
- `invariant/CabalInvariant.t.sol`: two campaigns, one for each IMD/CABAL ordering, each with 256 random sequences of 64 actions. Three users submit (with reasons that mix plain ASCII, quotes/backslashes and injection-shaped text, Latin-1/CJK, and emoji), approve/reject, execute, clear, transfer, donate, compound, and encounter configuration changes and time advances. Handler reverts fail the campaign; expected failures are asserted explicitly. A deterministic handler test verifies that buys, sells, callbacks, failures, clears, and compounding are reachable.

The invariants require fixed supply and conservation across every participating account; exact oracle charges; gate balances equal to unsolicited donations; equal burn/POL fees derived from the real PoolManager's swap deltas; zero residual settlement deltas and temporary approvals; request states matching the independent action history; and actual hook-owned position liquidity matching cumulative liquidity-addition events. Failed executions must preserve balances, pool price, fee accounting, request state, and holding records. The handler does not infer the expected fee from the hook's own fee counters.

Ordinary bounded trades use 400 minor units through 1,000 tokens, within the seeded pool's depth. Dedicated unit/fuzz tests cover smaller fee boundaries and full integer arithmetic. Random transfers can leave cost-basis records stale until the next gate interaction; the suite does not assert continuous ownership or known basis for transferred-in tokens.

The existing trading integration tests use production CABAL, Gate, Hook and Uniswap PoolManager code. The gate-only additions deploy CabalGate against mocks of its existing dependencies and never deploy CabalCoin or CabalHook; `GateLiveHook.t.sol` places the existing hook's runtime at its live address inside the test EVM to exercise the real binding and read paths, which is a test fixture, not a deployment. The launch deployment of the gate and its two helpers measures about 7.95 million gas through the rehearsal factory (24,443 + 5,888 + 3,737 bytes of runtime), which the deployment service's gas ceiling must accommodate. All tests run offline. The supplied protocol vector and captured live vectors check the wire schema and domain independently of signatures generated by the fixtures; they do not verify live deployment state.

The existing `HookBinding.t.sol` tests cover the original hook deployment's atomic initialization assumption. The current task reuses an initialized hook. The tree carries no `launch.json`: the manifest step writes it after this work is accepted. The constructor rehearsals use the brief's nineteen words.
